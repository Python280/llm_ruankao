## 一、数据库基本概念

### 1. 核心术语

| 术语 | 定义要点 |
|---|---|
| 数据（Data） | 描述事物的**符号记录**（文字、图形、图像、声音、语言等） |
| 信息（Information） | 现实世界事物的存在方式或状态的反映，具有可感知、可存储、可加工、可传递、可再生属性 |
| 数据库（DB） | 统一管理的、**长期储存**在计算机内的、有组织的相关数据集合；特点：联系密切、**冗余度小、独立性较高、易扩展、可共享** |
| 数据库管理系统（DBMS） | 数据库系统的**核心软件**，解决如何科学组织储存数据、高效获取和维护数据；需在**操作系统支持下**工作 |
| 数据库系统（DBS） | 采用数据库技术、有组织地动态存储大量相关联数据、方便多用户访问的计算机系统；广义含 DBMS。**组成：数据库、硬件、软件、人员** |

### 2. 数据管理技术三阶段

| | 人工管理 | 文件系统 | 数据库系统 |
|---|---|---|---|
| 特点 | ①数据量较少、面向应用、独立性差；②**数据不保存**；③**没有软件系统**对数据进行管理 | ①数据**可长期保留**，逻辑/物理结构有了区别；②数据不属于特定应用、可重复使用；③文件组织形式多样化（索引/链接/Hash） | ①采用**复杂的数据模型**表示数据结构，面向整个应用系统；②有**较高的数据独立性** |
| 缺点 | 应用程序与数据**依赖性太强**；数据组间**重复数据**造成冗余 | **数据冗余、数据不一致性、数据孤立**（数据联系弱） | — |
| 优点 | — | — | 对应用程序的**高度独立性**、数据的**充分共享性**、**操作方便性** |

> [!warning] 易错点
> 数据库系统与文件系统**重要的区别**是：**数据的充分共享、交叉访问、与应用程序的高度独立性**。"文件组织形式多样化"是**文件系统阶段**的特点，不是数据库系统的特点（练习 Q1 即考此点）。

### 3. 数据模型与数据库三代发展

**数据模型三要素**：

| 要素 | 含义 | 描述对象 |
|---|---|---|
| **数据结构** | 对象类型的集合 | 对系统**静态特性**的描述 |
| **数据操作** | 对实例允许执行的操作集合（检索、插入、删除、修改等） | 对系统**动态特性**的描述 |
| **数据的约束条件** | 一组完整性规则的集合 | 保证数据正确、有效、相容 |

**数据库发展的三个阶段**：

| 阶段 | 模型 | 要点 |
|---|---|---|
| 第一代 | **层次模型**（树形结构，根以外结点**有且仅有一个双亲**，上下层为 1:n 联系）、**网状模型**（允许一个以上结点无双亲/多个双亲；层次模型是其特例；**不能直接表示多对多联系**，需引入**联结记录**） | 共同特点：①支持**三级模式**体系结构；②用**存取路径**表示数据联系；③**独立**的数据定义语言；④**导航式**数据操纵语言 |
| 第二代 | **关系模型** | 用**表格结构**表达实体集及联系，最大特色是**描述的一致性**；关系模式≈记录型（类型定义），关系≈实例（变量） |
| 第三代 | 面向对象模型、语义数据模型、XML、半结构化模型等 | 最典型的是 **NoSQL** 运动（见第六节） |

### 4. DBMS 功能与特点

- **五大功能**：①**数据定义**（DDL，定义外模式/模式/内模式、完整性、安全保密，存于**数据字典**）；②**数据库操作**（DML，检索/插入/修改/删除）；③**数据库运行管理**（并发控制、安全性检查、完整性检查、日志、事务管理、自动恢复）；④**数据组织、存储和管理**；⑤**数据库的建立和维护**（初始建立、转换、转储恢复、重组重构、性能监测）
- **DBMS 通常分三类**：关系数据库系统 **RDBS**、面向对象数据库系统 **OODBS**、对象关系数据库系统 **ORDBS**
- **三大特点**：①数据**结构化且统一管理**（面向整个企业所有应用）；②有较高的**数据独立性**（物理独立性 + 逻辑独立性）；③**数据控制功能**（安全性、完整性、并发控制、故障恢复）

### 5. 三级模式—两级映像

| 模式 | 对应级别 | 内容 |
|---|---|---|
| **外模式**（子模式/用户模式） | 视图级 | 用户看到/使用的那部分数据的逻辑结构，对应数据库中的**视图** |
| **概念模式**（模式） | 概念级 | 全体数据的逻辑结构和特征描述，是所有用户的公共数据视图，对应**表**级别 |
| **内模式** | 物理级 | 数据物理结构和存储方式（内部记录类型、索引、文件组织方式） |

| 映像 | 保证的独立性 | 含义 |
|---|---|---|
| **外模式/概念模式映像** | **逻辑独立性** | 数据逻辑结构改变时，应用程序不变 |
| **概念模式/内模式映像** | **物理独立性** | 数据物理存储改变时，应用程序不变 |

自底向上：**物理级数据库（数据库文件）→ 概念级数据库 → 用户级数据库**。

### 6. 数据库系统体系结构四分类

| 类型 | 一句话特征 |
|---|---|
| **集中式数据库系统** | 所有东西集中在 **DBMS 所在电脑**上 |
| **客户端/服务器体系结构（C/S）** | 客户端负责**请求和数据表示**，服务器负责**数据库服务** |
| **并行数据库系统** | 多个**物理上在一起**的 CPU |
| **分布式数据库系统** | **物理上分布在不同地方**的计算机（详见第二节） |

## 二、分布式数据库

### 1. 体系结构（六层 + 四映像）

自上而下：**全局外模式 → 全局概念模式 → 分片模式 → 分布模式 → 局部概念模式 → 局部内模式 →（局部数据库）**

- **全局外模式（全局视图）**：全局应用的用户视图，是全局概念模式的子集，直接与用户/应用程序交互
- **全局概念模式**：定义数据的整体逻辑结构，"数据就如同根本没有分布一样"，可用集中式方法定义
- **分片模式**：将一个关系模式分解成几个**数据片**
- **分布模式（分配模式）**：定义**数据片段的存放节点**（分布式数据库的本质特性：数据分布在不同物理位置）
- **局部概念模式 / 局部内模式**：局部数据库自己的概念模式/内模式

结构划分：**映像 4（分布模式）以上**为"分布式数据库（**增加的**）"，由**全局 DBMS** 管理；**以下**为"集中式数据库（**原有的**）"，由**局部 DBMS** 管理。

**分布式数据库四大特点**：**共享性**（不同节点数据共享）、**自治性**（每个节点独立管理本地数据）、**可用性**（某场地故障可用其他场地副本，系统不瘫痪）、**分布性**（数据分布在不同场地）。

### 2. 分布透明性（高频考点）

用户不必关心数据的逻辑分片、物理位置分配细节、局部场地的数据模型。

| 透明性 | 层次 | 用户需要知道 | 用户无需知道 |
|---|---|---|---|
| **分片透明性** | **最高层次** | 只对全局关系操作 | **是否分片、如何分片** |
| **位置透明性** | 下一层次 | 分片情况 | **片段的存储场地** |
| **局部数据模型透明性（逻辑透明）** | 再下一层 | 分片及各片段存储场地 | **局部场地使用何种数据模型** |
| **复制透明性** | — | — | 结点的**复制情况**（数据从何而来） |

### 3. 分片与分区

**分片方式**（对应分片透明性）：

- **水平分片**：按**记录（行）**分，将表中水平记录分别存放在不同地方
- **垂直分片**：按**字段（列）**分，将表中垂直的列值分别存放在不同地方
- **混合分片**：两者结合

**分区、分表、分库**（案例特训口径）：

| | 分区 | 分表 |
|---|---|---|
| 共性 | ①都针对数据表；②都使用了分布式存储；③都提升了查询效率；④都降低了数据库的频繁 I/O 压力 | |
| 差异 | **逻辑上还是一张表**（物理拆成多个分区文件） | **逻辑上已是多张表**（如国内用户表/国外用户表） |

**分库**：将原本存放在一个实例上的众多分类数据分开存放到不同实例（如用户库、商品库），分散访问压力、利于差异化管理。

**三种分区方式**：

| 分区策略 | 说明 | 例 |
|---|---|---|
| **范围分区 RANGE** | 按数据范围值分区 | 用户编号 0-999999 → 分区A；1000000-1999999 → 分区B |
| **散列分区 HASH** | 对 key 做 hash 运算分区，类似取余 | 余数相同的放一个分区 |
| **列表分区 LIST** | 按某字段的某个具体值分区 | 长沙用户一个区、北京用户一个区 |

**分区五优点**：①可存储更多数据；②数据管理方便（清理/废弃某年数据直接删该分区）；③精准定位、免全表扫描，提高检索效率；④可跨多分区磁盘查询提高吞吐量；⑤聚合函数查询时容易合并数据。

### 4. 分布式事务管理：两阶段提交协议 2PC

**两个阶段**：

1. **表决阶段**：目的是**形成一个共同的决定**（参与者答复"建议提交/建议撤销"，协调者据此决定全局提交或全局撤销）
2. **执行阶段**：目的是**实现这个协调者的决定**

**两条全局提交规则**（原文必背）：

- **只要有一个参与者撤销事务，协调者就必须做出全局撤销决定**
- **只有所有参与者都同意提交事务，协调者才能做出全局提交决定**

活动图要点：协调者依次写 `begin_commit`、`commit/abort`、`end_trans` 到日志；参与者"准备提交"则写 `ready` 到日志进入就绪态，再按协调者消息写 `commit`/`abort` 并回确认。

### 5. DDBMS 组成与结构

- **组成**：**LDBMS**（局部）、**GDBMS**（全局）、**全局数据字典**、**通信管理（CM）**
- **结构**（按全局控制方式）：全局控制**集中**的 DDBMS、全局控制**分散**的 DDBMS、全局控制**部分分散**的 DDBMS

## 三、数据库设计六阶段

针对给定应用环境，创建性能良好的数据库模式、建立数据库及其应用系统。**一般分为 6 个阶段**（顺序必背）：

| # | 阶段 | 任务 | 产出物 |
|---|---|---|---|
| 1 | **用户需求分析** | 对应用对象的功能、性能、限制等要求进行分析；综合各用户应用需求，调查组织机构与业务活动，明确**信息要求、处理要求、系统要求**，确定新系统边界。方法：**自顶向下结构化分析（SA）**，用**数据流图 + 数据字典**逐层描述 | **数据流图、数据字典、需求说明书** |
| 2 | **概念结构设计** | 对信息分析和定义，精确抽象概括形成**独立于计算机系统**的概念模型；描述概念模型较理想的工具是 **E-R 图** | **E-R 模型（概念模型，与 DBMS 无关）** |
| 3 | **逻辑结构设计** | 将概念模型转换为与所选 **DBMS 支持的数据模型**相符的逻辑模型；包括模式初始设计、子模式设计、应用程序设计、模式评价、模式求精 | **关系模式**（+视图、完整性约束、应用处理说明书） |
| 4 | **物理结构设计** | 逻辑模型在计算机中的**具体实现方案**；输入 DBMS 特性与硬件/OS 特性 | 物理方案 |
| 5 | **数据库实施** | 建立实际数据库结构（DDL 脚本）、**数据加载**（装入）、**试运行和评价** | 可运行系统 |
| 6 | **数据库运行和维护** | 投入运行后不断**评价、调整与修改**；主要由 **DBA** 完成：性能监测和改善、备份及故障恢复、**重组和重构** | — |

> [!warning] 版本差异
> 官方教程的六阶段为"需求分析→概念→逻辑→物理→**实施**→**运行维护**"；32h 表述为"用户需求分析、概念结构设计、逻辑结构设计、物理结构设计、**应用程序设计**、运行维护"。**答题以官方六阶段顺序为准**。
> 物理设计三步：**确定数据分布、存储结构、访问方式**（存储结构含顺序/哈希/堆/B 树；常用索引提速；数据访问频率符合"**80/20 规则**"）。

## 四、概念结构设计（E-R 方法）

### 1. E-R 方法与三种抽象

概念结构设计的目标是产生**概念模式**，它**独立于**支持数据库的 DBMS 和硬件环境。最著名常用的是 **P.P.S. Chen 1976 年提出的实体-联系方法（E-R 方法）**，用实体、属性、联系描述现实世界的信息结构。

对现实事物抽象认识的 **3 种方法**：

| 方法 | 含义 |
|---|---|
| **分类（Classification）** | 按事物的共同特征和行为定义一种**类型** |
| **聚集（Aggregation）** | 定义某一类型所具有的**属性** |
| **概括（Generalization）** | 由已知类型（**超类**）定义新类型（**子类**），子类是超类的子集（is subset of，如研究生⊆学生） |

### 2. E-R 图三要素与画法

| 要素 | 图形 | 备注 |
|---|---|---|
| **实体（型）** | **矩形**框 | 框内标实体名 |
| **属性** | **椭圆**形 | 连线与实体相连 |
| **联系** | **菱形**框 | 标联系名，连线注明**联系类型** |

**联系类型**：一对一 **1:1**、一对多 **1:N**、多对多 **M:N**。

**属性分类**（一本通）：简单属性和复合属性（是否可分割）、单值属性和多值属性（取值个数）、NULL 属性（无意义）、派生属性（可由其他属性生成）。

### 3. 概念结构设计三步骤

1. **选择局部应用**：以**数据流图**为线索，选择适当层次（高层太笼统、底层太细），让该层每一部分对应一个局部应用
2. **逐一设计分 E-R 图（局部 E-R 图）**：从**数据字典**提取数据，用抽象机制确定实体、属性、实体标识符及联系与类型
3. **E-R 图合并**：将具有相同实体的分 E-R 图合二为一，合成实体属性取**并集**，逐步合并成**全局 E-R 图**

### 4. 合并时的三类冲突（必背）

| 冲突 | 含义 |
|---|---|
| **属性冲突** | 同一属性的**类型、取值范围、数据单位**等不一致 |
| **命名冲突** | 相同意义属性**命名不同**（同义异名），或名称相同属性**意义不同**（同名异义） |
| **结构冲突** | 同一实体在不同分 E-R 图中**属性不同**；或同一对象在一处被抽象为**实体**、在另一处被抽象为**属性** |

### 5. 合并中的三种优化

1. **实体类型的合并**：具有 **1:1 或 1:\*** 联系的两个实体可合并，减少实体个数、降低连接开销
2. **冗余属性的消除**：合并后某属性**可由其他属性确定**，即为冗余，应消除
3. **冗余联系的消除**：出现实体联系的**环状结构**（A 与 B 有直接联系，又经其他实体有间接联系），直接联系可由间接联系表达时，**消除直接联系**

## 五、逻辑结构设计（E-R → 关系模式）

### 1. 逻辑结构设计四步骤

**确定数据模型 → 将 E-R 图转换成指定的数据模型 → 确定完整性约束 → 确定用户视图**。

### 2. E-R 图转换为关系模式（必背）

**实体**：逐一转换成一个关系模式，实体名=模式名，实体属性=模式属性，**实体标识符=关系的码**。

**联系**三种转换规则：

| 联系类型 | 转换规则 |
|---|---|
| **1:1** | 通常**不**转换为独立关系模式；归并到关联两实体的**任意一方**——给待归并方增加**另一方实体的码 + 联系属性**，归并后**码不变** |
| **1:\*** | 通常**不**转换为独立关系模式；归并到**多方（N 端）**——给多方增加**一方实体的码 + 联系属性**，多方**码不变** |
| **\*:\*** | **只能**转换为**独立**关系模式；模式名=联系名，属性=**两个多方实体的码 + 联系属性**，码=**多方实体的码构成的属性组（联合主键）** |

### 3. 关系模式规范化（四步）

1. 根据**语义**确定各关系模式的数据依赖
2. 根据数据依赖确定**范式**（判定是否达到 3NF/BCNF）
3. 不符合要求则按**分解算法**分解至 3NF/BCNF
4. **评价及修正**：分解可消除冗余和更新异常，但按处理要求可能还需**增加部分冗余**（分解、合并、增加冗余属性），提高存储和处理效率

### 4. 完整性约束与用户视图

- **完整性约束**：数据项约束、表级约束、表间约束（检查约束、主码约束、参照完整性约束）
- **用户视图**：①按**数据流图**确定处理过程使用的视图（降低程序复杂性、提高数据独立性）；②按**用户类别**确定不同用户的视图（如各院系只见本院学生，提高**安全性**）

### 5. 反规范化

规范化导致关系概念单一化、多表关联查询性能下降，需对部分关系模式修正。**反规范化（Denormalization）是加速读操作性能（数据检索）的方法**，在标准化后**有选择地**添加特定冗余数据（注意：不能与"从未标准化"混淆）。

- **常见操作**：**冗余列、派生列、表重组、表分割**（表分割分**水平分割**与**垂直分割**）
- **代价**：形成数据冗余 → 设计复杂 + **更新异常** + 数据不一致
- **数据同步方法**：**应用程序同步、批量处理同步、触发器同步**

> 本节补肉自：官方教程 §6.3.4 p238-239（转换规则、规范化四步、完整性、用户视图、反规范化）、一本通 p57-58（1:1/1:N/M:N 转换口诀）。物理设计/实施/运行维护补肉自官方 §6.3.5-6.3.7 p239-242（80/20 规则、聚簇三原则、索引宜/不宜、重组≠重构）。

## 六、NoSQL 数据库

### 1. 概念与由来

- **NoSQL（Not only SQL）**：泛指**非关系型**数据库。一词**最早出现于 1998 年**，是 Carlo Strozzi 开发的一个轻量、开源、不提供 SQL 功能的关系数据库；**2009 年** Johan Oskarsson（Last.fm）发起讨论、Eric Evans（Rackspace）再次提出，当时主要指**非关系型、分布式、不提供 ACID** 的数据库设计模式
- 产生背景：应对**大规模数据集合和多重数据种类**的挑战，特别是大数据应用难题（超大规模、高并发的 Web 2.0 纯动态网站）

### 2. 关系数据库 vs NoSQL（六维对比）

| 对比维度 | 关系数据库 | NoSQL |
|---|---|---|
| 应用领域 | 面向通用领域 | 特定应用领域 |
| 数据容量 | 有限数据 | **海量数据** |
| 数据类型 | 结构化数据（二维表） | **非结构化数据** |
| 并发支持 | 支持并发、但性能低 | **高并发** |
| 事务支持 | 高事务性 | **弱事务性** |
| 扩展方式 | **向上扩展** | **向外扩展** |

### 3. NoSQL 四分类（必背）

| 分类 | 典型应用 | 数据模型 | 优点 | 缺点 | 举例 |
|---|---|---|---|---|---|
| **键值（key-value）** | 内容缓存、高访问负载、日志系统 | Key→Value 键值对，通常用 hash table 实现 | **查找速度快** | 数据无结构化，通常只当字符串/二进制数据 | **Redis**、Tokyo Cabinet/Tyrant、Voldemort、Oracle BDB |
| **列存储数据库** | 分布式文件系统 | 列簇式存储，同一列数据存在一起 | 查找快、**可扩展性强**、易分布式扩展 | 功能相对局限 | **HBase、Cassandra**、Riak |
| **文档型数据库** | Web 应用（Value 结构化，数据库能了解 Value 内容） | Key-Value，Value 为结构化数据 | 结构要求不严格、**表结构可变**、无需预定义表结构 | 查询性能不高、**缺乏统一查询语法** | **CouchDB、MongoDB** |
| **图形数据库（Graph）** | 社交网络、推荐系统，构建关系图谱 | 图结构 | 可利用图算法（**最短路径寻址、N 度关系查找**） | 常需全图计算；**不好做分布式集群方案** | **Neo4J**、InfoGrid、Infinite Graph |

### 4. NoSQL 特征与适用情况

- **特征**（32h）：**易扩展、大数据量、高性能、灵活的数据模型、高可用**
- **适用情况**：数据模型比较简单、需要灵活性更强的 IT 系统、对数据库性能要求较高、**不需要高度的数据一致性**
- **体系框架**（自下而上四层）：**数据持久层 → 数据分布层 → 数据逻辑模型层 → 接口层**
