# 测试方法与阶段

> [!note] 考情（★★，讲义 p62-72）
> 讲义 p62 标注：**软件测试方法（★★）**、软件调试（★，讲义无专门内容页，仅点到）。本节覆盖：测试分类与静态分析四项（p63）、白盒/黑盒方法（p64）、测试阶段与依据文档（p67）、其他测试含 AB 测试（p68）、集成策略（p69）、性能测试子类（p70），配 4 道真题（p65/66/71/72）。官方 §5.4 补各阶段特征与 Alpha/Beta；大纲 4.4 补 **V&V** 与逻辑覆盖六级。
>
> **【软件测试】** 是使用人工或自动的手段来运行或测定某个软件系统的过程，目的在于**检验它是否满足规定的需求**或弄清预期结果与实际结果之间的差别；测试要**贯穿在整个软件开发的过程中**（官方 §5.4）。

## 一、测试方法三分类（讲义 p63，官方 §5.4.1）

| 分类依据 | 分类 |
|---|---|
| 程序**执行状态** | 静态测试 ST / 动态测试 DT |
| 与**具体实现算法细节和系统内部结构**的相关情况 | 黑盒 / 白盒 / 灰盒测试 |
| 程序**执行方式** | 人工测试 MT / 自动化测试 AT |

### 静态 vs 动态（讲义 p63）

| 测试类型 | 手段 | 方法 | 说明 |
|---|---|---|---|
| 动态测试 | 【计算机运行】 | 白盒测试法、灰盒测试法、黑盒测试法 | 分别关注内部结构与逻辑、介于两者之间、关注输入输出及功能 |
| 静态测试 | 【人工监测和计算机辅助分析】 | **桌前检查、代码审查、代码走查** | 都是做的【静态分析】 |

> [!important] 记忆点
> 静态三件套＝**桌前检查、代码审查、代码走查**（讲义 p65 真题第二空原话）；动态测试的手段必带"**计算机运行**"。

### 静态分析四项（讲义 p63）

| 分析 | 检查内容 |
|---|---|
| 控制流分析 | 是否存在**没有使用的语句 / 无法达到的语句 / 调用并不存在的子程序** |
| 数据流分析 | **引用未定义的变量**、对以前未使用的变量再次赋值；"**数据初始化、赋值或引用过程中的异常**" |
| 接口分析 | 模块之间接口的一致性、子程序和函数之间的接口一致性、函数**形参与实参的数量、顺序、类型**的一致性 |
| 表达式分析 | **括号不配对、数组引用越界、除数为零** |

### 自动化测试（讲义 p63，大纲 4.4.1）

先写脚本 → 自动化执行。**不适合场景：项目周期短，需求变动频繁**。大纲表述：测试脚本设计和测试用例自动生成。

## 二、黑盒 / 白盒 / 灰盒（讲义 p64，官方 §5.4.1）

### 白盒测试【结构测试】

借助程序内部逻辑和相关信息，检查每一条通路能否正常工作；主要用于**单元测试阶段**。

| 白盒测试方法 | 说明 |
|---|---|
| 控制流测试 | 即【逻辑覆盖测试】：**语句覆盖最弱，路径测试覆盖最强** |
| 数据流测试 | |
| 程序变异测试 | 【错误驱动测试】 |

#### 逻辑覆盖六级（弱→强）（讲义 p64 + 大纲 4.4.2）

| 覆盖准则 | 含义 |
|---|---|
| 语句覆盖（最弱） | 每条可执行语句至少执行一次 |
| 判定覆盖 | 每个判定的取真、取假分支至少各执行一次 |
| 条件覆盖 | 判定内每个原子条件的真、假取值至少各出现一次 |
| 判定/条件覆盖 | 同时满足条件取值与判定结果的取真取假 |
| 条件组合覆盖 | 每个判定内各条件取值的所有组合至少出现一次 |
| 路径覆盖（最强） | 程序中所有可能路径至少执行一次 |

> [!warning] 易错点
> - 判定覆盖与条件覆盖**互不包含**（判定取真不代表所有条件都取真），二者均强于语句覆盖；判断题爱拿这两级比大小。
> - 讲义只点到"语句覆盖最弱、路径测试覆盖最强"，六级体系为大纲标准知识；官方教程仅列语句、判定、分支、路径四级。

### 黑盒测试【功能测试】

把程序看成黑盒，不考虑内部结构，依据需求规格说明书设计测试用例，主要测试软件界面和功能；主要用于**集成测试、确认测试和系统测试阶段**。

| 黑盒测试方法 | 说明 |
|---|---|
| 等价类划分 | 不同等价类揭示不同问题；**有效等价类 / 无效等价类** |
| 边界值分析 | 1≤x≤10 时，可取 x＝**0、1、10、11** 作为测试数据 |
| 错误推测 | 依靠测试人员的**经验和直觉** |
| 判定表 | 最适合描述**多个逻辑条件取值的组合**所构成的复杂情况下，分别要执行哪些不同的动作 |
| 因果图 | 根据**输入条件与输出结果之间的因果关系**来设计测试用例 |

> [!important] 高频辨析
> **判定表**＝条件组合→动作；**因果图**＝因果关系→测试用例。二者定义互换是常考点；错误推测的定义也常被张冠李戴给因果图。

### 灰盒测试（官方 §5.4.1，讲义 p63 点到）

介于黑盒与白盒之间：既重视输出相对于输入的正确性，也看重内部程序逻辑，但**不像白盒那样详细和完整**。在"内部结果有错、输出结果正确"的情况下采用灰盒：**比白盒高效、比黑盒适用性广**。

> [!tip] 来源：官方教程 §5.4.1（印刷 p205-206）、讲义 p63-64

## 三、测试阶段（讲义 p67-70，官方 §5.4.2，大纲 4.4.2）

大纲列举的阶段：**单元测试、集成测试、系统测试、性能测试、验收测试和 AB 测试**。讲义主线四阶段（单元→集成→系统→确认），验收测试是确认测试的最后一环，官方又将验收测试作为**最后一个阶段**的测试。

### 四阶段主线与依据文档（讲义 p67）

| 阶段 | 依据 | 测试内容 |
|---|---|---|
| 单元测试 | 【详细设计】 | 模块测试：模块功能、性能、接口等 |
| 集成测试 | 【概要设计】 | 模块间的接口 |
| 系统测试 | 【需求文档】 | 功能测试、性能测试、验收测试、压力测试等 |
| 确认测试 | 【需求文档】 | 验证**软件与需求的一致性**：内部确认测试、Alpha 测试、Beta 测试、验收测试 |

> [!important] 记忆点
> 依据文档：**单元＝详细设计，集成＝概要设计，系统/确认＝需求文档**；判断题最爱互换依据。

### 各阶段要点（官方 §5.4.2，32h §7.4）

| 阶段 | 要点 |
|---|---|
| 单元测试 | 测模块，发现功能不符合期望与编码错误；先静态测试（静态分析、代码审查）再动态；可黑盒提出例再用白盒增补；往往由**程序员自己**完成（32h） |
| 集成测试 | 对已组装模块同时测试，验证组装正确性、发现**接口**有关问题；**白盒与黑盒结合** |
| 系统测试 | 一般采用**黑盒**，由**独立的测试小组**进行，需多轮**回归测试**；**结束标志**＝满足需求覆盖率＋缺陷全部归零 |
| 验收测试 | **最后一个阶段**、正式交付前；满足用户需求或合同要求；由**用户**开展 |

### 验收测试与 Alpha / Beta（官方 §5.4.2）

- **Alpha 测试**：在**软件开发环境下**由用户进行的测试，或模拟实际操作环境进行的测试；评价功能、局域化、界面、可使用性以及性能等。
- **Beta 测试**：在**实际环境中**由多个用户对其进行测试，并将发现的错误有效反馈给软件开发者。

> [!warning] 易错点
> Alpha＝开发环境/模拟环境（内部），Beta＝实际环境（外部多用户）——两者环境互换是常年考题。

### 集成测试策略（讲义 p69）

| 策略 | 特点 |
|---|---|
| 一次性组装 | 【风险高】 |
| 增量式组装 | 【测试全面】 |

增量式三种：**自顶向下**→需要【桩模块】（stub：模拟被测模块所调用的子模块）；**自底向上**→需要【驱动模块】（driver：调用被测模块、送入测试用例并输出结果）；**混合式**→桩模块和驱动模块都需要。

> [!important] 记忆点
> **顶桩底驱**：自顶向下配桩（下面子模块还没实现），自底向上配驱动（上面调用者还没组装）。

### 系统测试内容与性能测试子类（讲义 p70）

系统测试项：功能测试、性能测试、健壮性测试、用户界面测试、安全性测试、安装与反安装测试。

| 性能子类 | 口诀 | 含义 |
|---|---|---|
| 负载测试 | 看变化 | 各种工作负载下系统的性能 |
| 压力测试 | 【测上限】 | 系统的**瓶颈或不能接受的性能点** |
| 强度测试 | 【测下限】 | 系统**资源特别低**的情况下运行 |
| 容量测试 | 【并发测试】 | **同时在线的最大用户数** |
| 可靠性测试 | 算指标 | MTTF 之类的参数 |

> [!tip] 记忆点：上限＝压力（瓶颈），下限＝强度（资源低），并发＝容量（最大在线人数）。
> 来源：讲义 p69-70

## 四、其他测试（讲义 p68，官方 §5.4.2）

| 测试 | 描述 |
|---|---|
| AB 测试 | 多版本同时使用，利于收集各版本的用户反馈，评估出最好版本。故也算是一种【**网页优化方法**】 |
| Web 测试 | 与其他系统测试内容基本相同，只是测试重点不同；Web 代码测试包括源代码规则分析、链接测试、框架测试、表格测试、图形测试等 |
| 链接测试 | ①所有链接是否确实链接到指示的页面 ②所链接的页面是否存在 ③保证没有孤立的页面 |
| 表单测试 | 验证服务器能否正确保存数据、后台程序能否正确解释和使用；测试提交操作的完整性 |
| 回归测试 | 软件变更之后，**变更部分的正确性**和对变更需求的符合性 |

> [!tip] 来源：讲义 p68、官方教程 §5.4.2（印刷 p207-208）

## 五、V&V 验证与确认（大纲 4.4.1）

> [!warning] 无旁证
> 大纲 4.4.1 明确列出"验证与确认（V&V）"，讲义 p62-72 与官方 §5.4 均无专节 → **无旁证**，按以下通行定义记，考试跟大纲。

| | 验证 Verification | 确认 Validation |
|---|---|---|
| 回答的问题 | **是否正确地构造了产品？** | **是否构造了正确的产品？** |
| 标准 | 符合规格说明/设计文档 | 满足用户实际需要 |
| 手段 | 贯穿全程的测试、评审、静态分析 | 确认测试、验收测试、Alpha/Beta |

- 讲义呼应：**确认测试**＝验证软件与需求的一致性（p67），即 validation 在测试阶段的落地。
- 测试的目的（32h §7.4）：确保软件质量、确认软件以正确的方式做了用户所期望的事情；通常在规定的时间和成本内完成，**尽量多地发现漏洞，但不能保证发现所有的漏洞**。
