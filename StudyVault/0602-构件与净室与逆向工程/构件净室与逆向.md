# 构件、净室与逆向工程

> [!note] 考情（★-★★，讲义 p12-13、p25-29）
> 讲义 p2 提要：**基于构件的软件工程 CBSE★★、逆向工程★、净室软件工程★**。官方教程有完整对应节（§5.5 净室 / §5.6 CBSE），定义以官方为准。高频选择题：构件五特征、构件模型三要素、组装三方式与三种不兼容、净室"正确性验证而非测试"、盒结构三视图、逆向工程四抽象层次（讲义 p27 有真题）。

## 一、基于构件的软件工程（CBSE，讲义 p12-13）

### 1. 定义与哲学

**CBSE（Component-Based Software Engineering）** 是一种基于分布对象技术、强调通过**可复用构件**设计与构造软件系统的软件复用途径。构件可以是 **COTS（商用现成）构件**，也可以是自行开发等其他途径获得的构件。

- CBSE 体现了**【购买而不是重新构造】**的哲学（Fred Brooks"购买，而非建造"）；
- 开发重点从**程序编写**转移到**基于已有构件的组装**，工程师的焦点从"**实现**"变成"**集成**"。

### 2. 构件五特征（讲义 p12）

| 特征 | 内涵 |
|---|---|
| **可组装性** | 所有外部交互必须通过**公开定义的接口**进行 |
| **可部署性** | 构件总是**二进制形式**的，能作为一个**独立实体**在构件平台上运行（自包含，部署前无须编译） |
| **文档化** | 构件必须完全文档化，用户**根据文档**来判断构件是否满足需求 |
| **独立性** | 可以在**无其他特殊构件**的情况下进行组装和部署；如确实需要其他构件提供服务，应**显式声明** |
| **标准化** | 必须符合某种**标准化的构件模型** |

> [!warning] 易错点
> 五特征里**没有**"可测试性""可维护性"这类质量属性词——选择题常用它们做干扰项。可部署性的题眼是"**二进制**"。

### 3. 构件模型三要素（官方 §5.6.1 补）

构件模型定义了构件**实现、文档化以及开发**的标准。目前主流的构件模型：**Web Services 模型、Sun 公司的 EJB 模型、微软的 .NET 模型**。

构件模型包含三个基本要素（大纲 §4.6.1 明列）：

| 要素 | 要点 |
|---|---|
| **接口** | 构件通过构件接口来定义；模型规定接口定义中应包含的要素，如**操作名、参数、异常**等 |
| **使用信息** | 构件须有**全局唯一的名字或句柄**；构件**元数据**（接口和属性信息）供用户找到构件提供的服务；部署时须对构件**配置**以适应应用系统 |
| **部署** | 规格说明指出如何**打包**构件使其成为独立可执行实体；构件模型提供两类通用服务——**平台服务**（分布式环境下通信互操作）与**支持服务**（如身份认证等共性服务） |

**容器**：可认为构件被部署在容器中。容器是**支持服务的一个实现加上一个接口定义**，构件必须提供该接口定义以便和容器整合在一起。

### 4. CBSE 过程（大纲 §4.6.2 五步）

**大纲五步**（按序）：

①**系统需求概览** → ②**识别候选构件** → ③**根据发现的构件修改需求** → ④**体系结构设计** → ⑤**组装构件，创建系统**

> [!warning] 五步 vs 六项
> 官方教程 §5.6.2 在④⑤之间多一项"**构件定制与适配**"（共 6 项主要活动）。考试按**大纲五步**记框架，但选项中冒出"构件定制与适配"时知道它属于 CBSE 过程即可。

**CBSE 过程与传统开发过程的不同**（官方）：

- CBSE **早期需要完整的需求**，以便尽可能多地识别出可复用构件（增量式开发则不需要）；
- 在过程早期阶段**根据可利用的构件来细化和修改需求**——构件满足不了需求时，可劝说用户修改需求以节省开支、快速开发；
- **体系结构设计阶段特别重要**：此阶段选择构件模型和实现平台，模型和平台**决定和限制了可选构件的范围**。

### 5. 构件组装三方式（讲义 p13）

构件组装是指构件相互直接集成、或用专门编写的**"胶水代码"**将它们整合在一起来创造一个系统或另一个构件的过程。

| 方式 | 要点 |
|---|---|
| **顺序组装** | 按顺序调用已存在的构件，可用两个已存在的构件创造新构件；需胶水代码保证**上一个构件的输出与下一个构件的输入兼容** |
| **层次组装** | 一个构件**直接调用**另一个构件提供的服务；被调用构件的"**提供**"接口必须和调用构件的"**请求**"接口**兼容**，不匹配则写胶水代码转换 |
| **叠加组装** | 多个构件合并形成**新构件**，新构件整合原构件功能、对外提供**新的接口**；原有构件**不互相依赖、不互相调用** |

**组装可能出现的 3 种不兼容**（接口不一致）：

| 不兼容 | 定义 |
|---|---|
| **参数不兼容** | 接口每一侧的操作**名字相同**，但**参数类型或参数个数**不相同 |
| **操作不兼容** | 提供接口和请求接口的**操作名不同** |
| **操作不完备** | 一个构件的提供接口是另一个构件请求接口的**子集**（或相反） |

解决方式：编写**适配器构件**——使两个可复用构件的接口相一致，将一个接口转换为另一个接口。

## 二、净室软件工程（CSE，讲义 p28-29）

### 1. 定义与哲学

**净室**即无尘室、洁净室——一个**受控污染级别**的环境。

**净室软件工程（Cleanroom Software Engineering，CSE）** 是一种应用**数学与统计学理论**、以经济的方式生产高质量软件的工程技术，力图通过严格的工程化的软件过程达到开发中的**零缺陷或接近零缺陷**。

- 不是先做出产品再消除缺陷，而是**在规约和设计中消除错误**，然后以"净"的方式制作；
- 哲学：**第 1 次正确地书写代码增量，并在测试前验证其正确性**，避免对成本很高的错误消除过程的依赖；
- 甚至提倡开发者**不需要进行单元测试**，而是进行**正确性验证和统计质量控制**；
- 净室是**基于理论、面向工作组**的方法。

### 2. 理论基础（官方 §5.5.1 补）

- **函数理论**：程序的规范就是一个函数的规范。明确定义的函数须具备**完备性**（每个输入都有输出对应）、**一致性**（每个输入只对应一个输出）、**正确性**（可由上述性质推理验证）；
- **抽样理论**：不可能测试软件的所有可能应用，把全部使用情况看作**总体**，通过统计学手段**抽样**测试，据测试结果分析性能和可靠性。

### 3. 四大技术手段（讲义 p28，"统计过程/盒结构/增量认证"）

| 技术手段 | 要点 |
|---|---|
| **统计过程控制下的增量式开发** | 基于受控迭代的工程原理——**控制迭代**；不把整个开发过程作为整体，而是划分为一系列较小的**累积增量** |
| **基于函数的规范和设计（盒结构）** | 按函数理论定义 **3 种抽象层次**：**行为视图（黑盒）→ 有限状态机视图（状态盒）→ 过程视图（明盒）**；盒子结构基于对象，支持信息隐藏和实现分离 |
| **正确性验证** | 净室工程的**核心**，正是它使净室项目软件质量极大提高 |
| **统计测试和软件认证** | 先确定**使用模型**代表系统所有可能使用的（一般无限的）总体，由使用模型产生测试用例；测试用例是总体的随机样本 → 得到预期操作性能的有效统计推导。**总体太大时必须采用抽样方法** |

> [!important] 高频辨析
> 净室强调将**正确性验证**（而**不是测试**）作为发现和消除错误的主要机制——判断题最爱把"测试"与"正确性验证"对调。

### 4. 缺点（讲义 p29）

1. **太理论化**：需要更多数学知识，正确性验证的步骤比较困难且耗时，开发成本比较高昂；
2. 开发小组**不进行传统的模块测试，这是不现实的**（工程师可能不熟悉语言环境，编译器/操作系统 bug 也可能导致未预期的错误）；
3. 脱胎于传统软件工程，不可避免带有传统软件工程的一些弊端。

### 5. 应用（官方 §5.5.3 补）

第一项净室软件项目由 **IBM 的 Richard Linger** 于 20 世纪 80 年代中期负责实施（COBOL 结构化设施项目）；此后 NASA 哥达德飞行控制中心、美国陆军（获 20 倍投资回报）等均有成功实践。

## 三、逆向工程（讲义 p25-26）

### 1. 定义与再工程流程

**逆向工程（Reverse Engineering）**：分析程序，力图在**比源代码更高抽象层次**上建立程序的表示过程。**逆向工程是设计的恢复过程**（红字原话）。

再工程流程（讲义 p25 图）：现有系统 → 再工程 → 新系统；再工程展开为三步：**逆向工程 → 考虑新需求 → 正向工程**。

### 2. 导出信息的四个抽象层次（★讲义 p27 真题）

| 层次 | 包括的信息 | 例 |
|---|---|---|
| **实现级** | 程序的**抽象语法树、符号表**、过程的设计表示 | 最贴近代码 |
| **结构级** | 反映**程序分量之间相互依赖关系**的信息 | 调用图、结构图、程序和数据结构 |
| **功能级** | 反映**程序段功能及程序段之间关系**的信息 | 数据和控制流模型 |
| **领域级** | 反映**程序分量或程序诸实体与应用领域概念之间对应关系**的信息 | 实体关系模型 |

**四级趋势**（32h 表 7.4）：自实现级 → 领域级，**抽象级别递增、恢复难度递增、工具支持可能性递减、人工参与程度递增**。

### 3. 五个相关概念（讲义 p26）

| 概念 | 定义 |
|---|---|
| **重构/重组（Restructuring）** | 在**同一抽象级别**上**转换系统描述形式** |
| **设计恢复（Design recovery）** | 借助工具从已有程序中抽象出有关**数据设计、总体结构设计和过程设计**等方面的信息 |
| **逆向工程（Reverse engineering）** | 分析程序，力图在**比源代码更高抽象层次**上建立程序的表示；是设计的恢复过程 |
| **正向工程（Forward engineering）** | 不仅从现有系统中**恢复设计信息**，而且**使用该信息去改变或重构**现有系统，以改善其整体质量 |
| **再工程/重构工程（Re-engineering）** | 对现有系统的**重新开发过程**，包括**逆向工程、新需求的考虑过程和正向工程**三个步骤 |

> [!warning] 易错点
> **重构＝同一抽象级别**转换描述形式；**逆向工程＝升到更高抽象级别**；**正向工程＝恢复信息并用它改造系统**——三者的"抽象级别方向"是判断题互换的重灾区。
