# 数据库设计案例 · 解题方法

## 设计阶段速览（案例题干的常见背景）

- **概念结构设计**四步：抽象数据 → 设计局部 E-R 模型 → **合并局部模型、消除冲突** → **重构优化、消除冗余**（案例特训 p6）。
- **逻辑结构设计**四步：转化为数据模型 → **关系规范化** → 模式优化 → 设计用户子模式（案例特训 p9）。输入是"转换规则、规范化理论"，输出是关系模式。
- 官方教程六阶段：用户需求分析 → 概念结构设计 → 逻辑结构设计 → 物理结构设计 → 数据库实施 → 数据库运行和维护（官方教程 §6.3.1）。
- 数据库设计关注的三大问题：**性能、数据一致性、安全**（案例特训 p16）——案例题的三大矛盾几乎都从这里出题。

> [!tip] 来源：官方教程 §6.3 p234–242（印刷）

## 题型一：E-R 图设计（实体识别 / 联系基数 / 模式转换）

### 1. 三要素识别

| 图形 | 含义 | 识别技巧 |
|---|---|---|
| 矩形 | **实体** | 角色（管理员/经理）、业务对象（订单/项目）、**数据存储/数据表往往对应实体** |
| 椭圆 | **属性** | 带**下划线**的属性是**主键**（案例特训 p5） |
| 菱形 | **联系** | 联系名多为动词：填报、审核、确认、选课…… |

- 基数标注：连线上的 **1 / n / M / N**（或 *）。M:N 联系的**联系本身可以带属性**（如"选课"带"成绩"，案例特训 p5）。

### 2. 三类冲突（合并局部 E-R 图时必背）

| 冲突 | 含义 | 官方表述要点 |
|---|---|---|
| **属性冲突** | 同一属性在不同分 E-R 图中**类型、取值范围、数据单位**不一致 | 将来只能以一种形式存储，需在设计阶段统一 |
| **命名冲突** | 相同意义的属性**命名不同**；或**同名属性**在不同分 E-R 图中代表不同意义（同名异义） | 需要统一命名 |
| **结构冲突** | 同一实体在不同分 E-R 图中**属性不同**；或同一对象在一处被抽象为**实体**、在另一处被抽象为**属性** | 需要统一抽象层次 |

合并后的优化三手段：**实体类型的合并**（1:1 或 1:n 联系的两个实体可合并，减少连接开销）、**冗余属性的消除**（某属性可由其他属性确定）、**冗余联系的消除**（环状结构中直接联系可被间接联系表达时，消除直接联系）。

> [!tip] 来源：官方教程 §6.3.3 p236–237（印刷）

### 3. E-R 图 → 关系模式转换规则（官方标准表述）

| 对象 | 转换规则 |
|---|---|
| **实体** | 逐一转换成一个关系模式：实体名→模式名，实体属性→模式属性，**实体标识符就是关系的码** |
| **1:1 联系** | 通常**不独立成模式**，归并到任一方实体：给该方属性集增加**另一方实体的码**和该联系的属性，归并后码不变 |
| **1:n 联系** | 通常**不独立成模式**，归并到**多方（n 方）**：给多方实体增加**一方实体的码**和该联系的属性，多方实体的码不变 |
| **m:n 联系** | **必须转换成独立的关系模式**：模式名取联系名，属性 = 两个多方实体的码 + 联系的属性，**码 = 两个多方实体的码构成的属性组** |

> [!tip] 来源：官方教程 §6.3.4 p238（印刷）
> **外键判定**：归并进来的一方实体的码，在归并后的关系中就是**外键**。题目问"指出主键/外键"时按此规则直接套。

### 4. 补充属性 / 主外键的常见问法

- **补充实体**：题干给数据流图 + 不完整 E-R 图，要求填实体名。解法：数据流图中的**数据存储（XX表）与外部角色**就是实体候选；用 E-R 图上已有连线和基数**逐个代入验证**。
- **补充属性**：看单据/表单题（如包裹单），表单栏目即属性；能从其他属性**计算得出**的是**派生属性**（如"总计=资费+挂号费+保价费+回执费"）。
- **超类实体**：将多个实体中**相同的属性**组合起来构造出的新实体（如收件人与寄件人共有的"姓名、电话、单位名称、详细地址"→ 超类"用户"）。

### 5. 解题步骤模板

1. 读数据流图：圈出**外部实体（角色）**和**数据存储（表）**——它们对应 E-R 图的实体；
2. 读 E-R 图：从待填实体出发的**联系名与基数**（1/n）就是约束条件；
3. 代入验证：每个待填实体代回后，检查其参与的每个联系的基数是否成立；
4. 注意"同一实体的不同叫法"（如"项目管理员"既出现在数据流图又是 E-R 图实体）。

### 真题示范：煤矿建设项目安全预警系统 E-R 图补充实体

**题干摘要**（案例特训 p7，题干全文见 [[练习题-数据库设计案例]] Q1）：根据数据流图补充完善总体 E-R 图中实体（1）～（6）的具体内容。

**参考答案（逐字）**：

> （1）项目管理员
> （2）项目经理
> （3）项目指标数据
> （4）～（6）指标参数、项目信息、事故及影响因素参数

**解析**：数据流图中的外部角色"项目管理员""项目经理"直接对应实体（1）（2）；数据存储"项目指标数据表""指标参数表""项目信息表""事故及影响因素参数表"对应实体（3）～（6）。E-R 图中（3）与"安全员-填报（1:n）""安全副经理-审核（n:1）"相连，说明（3）是被填报、被审核的业务数据——即**项目指标数据**；（4）（5）（6）均与"创建""分析"联系相连，对应三张参数/信息表（顺序不限）。

## 题型二：规范化案例（逻辑模型设计 / 候选码 / 范式 / 反规范化）

### 1. 案例中的四种问法

| 问法 | 典型真题 |
|---|---|
| 逻辑数据模型设计过程包含哪些任务？应含哪些实体、主键是什么？ | 包裹信息管理系统（Q2） |
| 给定关系模式和语义，判定候选码/范式级别，说明理由 | 2020 规范化数据库设计（考情表） |
| 关系表过细导致多表连接性能差，采用什么**反规范化**方法改造？ | 医药销售系统（Q3） |
| 反规范化带来的**数据不一致**如何解决？ | 医药销售系统（Q3）、电商视图（Q4） |

### 2. 候选码判定速法

- **属性闭包法**：从只在依赖箭头**左边出现**的属性出发求闭包，若能推出全部属性且无冗余，即为候选码；
- 组成候选码的属性是**主属性**，其余是**非主属性**；所有属性组都是候选码称为**全码（ALL-Key）**（案例特训 p10）。

### 3. 范式判定速查（案例特训 p18 逐字）

| 范式 | 要求（逐步优化，解决数据冗余、插入、修改、删除异常） |
|---|---|
| **1NF** | 属性值都是**不可分的原子值** |
| **2NF** | 消除**非主属性**对候选键的**部分依赖** |
| **3NF** | 消除**非主属性**对候选键的**传递依赖** |
| **BCNF** | 消除**主属性**对候选键的**部分和传递依赖** |

- **部分依赖**例：候选键（学号，课程号）中，课程号→课程名（只依赖候选键的一部分）；成绩→依赖整个候选键，非部分依赖。
- **传递依赖**例：学号→班级号→班级名。
- 思考题（p18）：范式级别提升的负面影响 = **关系拆得越细，多表连接查询越多，查询性能下降**——这正是反规范化案例的题干背景。

### 4. 反规范化四技术 + 优缺点（案例特训 p19–20）

| 技术手段 | 说明 |
| --- | --- |
| **增加派生性冗余列** | 已有单价和数量列，增加"总价"列（可由其他数据计算生成） |
| **增加冗余列** | 已有学号列，增加"姓名"列（多个表中具有相同的列，避免连接） |
| **重新组表** | 把常需连接查询的两张拆分表重新合成一张表 |
| **分割表** | 水平分割：长沙的用户存在长沙，上海的用户存在上海 |

- **优点**：连接操作少，检索快，统计快，需要查的表减少，检索容易。
- **缺点**：数据冗余占更多存储空间；插入/更新/删除开销更大；**数据不一致**（可能产生添加、修改、删除异常）；更新和插入代码更难写。
- **数据不一致的解决**：①**触发器数据同步**；②**应用程序数据同步**；③**批处理同步**（官方教程 §6.3.4 表述为"应用程序同步、批量处理同步和触发器同步"）。

> [!important] 答题模板
> 问"采用哪种反规范化方法"时：**先列四种方法定义，再结合查询场景选一种并说明理由**（查 A 表要显示 B/C 表的列 → 增加冗余列；两表总是一起连接查询 → 重新组表；统计汇总值 → 增加派生列；按地域/时间分散访问 → 分割表）。

### 5. 解题步骤模板

1. 写出/读出关系模式的**函数依赖**（按语义）；
2. 求**候选码**，划分主属性/非主属性；
3. 按"部分依赖→2NF，传递依赖→3NF，主属性依赖→BCNF"逐级判定；
4. 不满足则**分解**（分解到 3NF/BCNF，注意保持无损与函数依赖）；
5. 若题干转向性能问题 → 转反规范化四技术 + 数据不一致三对策。

### 真题示范：包裹信息管理系统（逻辑数据模型/超类实体/派生属性）

**题干摘要**（案例特训 p11–12，全文见 [[练习题-数据库设计案例]] Q2）：某企业开发包裹信息管理系统，对邮政包裹单建模。问题1 问逻辑数据模型设计过程的任务、包含哪些实体及各自主键（14分）；问题2 问超类实体（6分）；问题3 问派生属性（5分）。

**参考答案（逐字）**：

> 【问题1】逻辑数据模型设计过程包含的任务：
> （1）构建系统上下文数据模型，包含实体及实体之间的联系；
> （2）绘制基于主键的数据模型，为每个实体添加主键属性；
> （3）构建全属性数据模型，为每个实体添加非主键属性；
> （4）利用规范化技术建立系统规范化数据模型。
> 包裹单的逻辑数据模型中包含的实体：
> （1）收件人（主键:电话）；
> （2）寄件人（主键:电话）；
> （3）包裹单（主键:编号）。
>
> 【问题2】超类实体是将多个实体中相同的属性组合起来构造出的新实体。
> 用户（姓名、电话、单位名称、详细地址）
>
> 【问题3】派生属性是指某个实体的非主键属性由该实体其他非主键属性决定。
> 包裹单中的总计是由资费、挂号费、保价费、回执费计算得出，所以是派生属性。

**解析**：包裹单表单栏目直接映射属性；收件人/寄件人属性高度重合 → 抽取超类"用户"；"总计"可由其他费用栏加总 → 派生属性。

## 题型三：缓存与分布式（Redis / 一致性 / 读写分离 / 分片 / 2PC）

### 1. Redis 使用场景与数据类型

- Redis 属 **Key-Value 型 NoSQL**：内容缓存，处理大量数据的高访问负载、日志系统；查找速度快（案例特训 p47）。
- 五种数据类型（案例特训 p23）：**String、Hash、List、Set、ZSet**。
- **选型口诀**：**排名/排行榜 → ZSet（有序集合）**；简单缓存键值 → String；对象字段 → Hash；列表/队列 → List；去重集合 → Set。
- 混合架构动机：将热点关系数据放到内存中以提高查询性能（如热销商品排名），但带来 **Redis 与 MySQL 的数据实时同步问题**。

### 2. 缓存-数据库一致性四方法（必背，案例特训 p25/p54 逐字）

1. **实时同步方案**：先查缓存，查不到再从 DB 查询，并保存到缓存；更新缓存时**先更新数据库，再将缓存设置过期**。
2. **异步队列方式同步**：可采用消息中间件处理。
3. 通过**数据库插件**完成数据同步。
4. 利用**触发器**进行缓存同步。

### 3. 读写分离与主从复制（2023 考点）

- 读写分离：主服务器负责**写**操作，从服务器负责**读**操作 → 减少数据并发操作的**锁争用**，但带来了**数据冗余** → 需要主从复制策略保持数据**一致性**。
- MySQL 主从复制通过 **binary log** 实现，三种复制类型：**基于SQL语句的复制（SBR）、基于行的复制（RBR）、混合模式复制（MBR）**。
- 性能优化结构图（案例特训 p17）：集中式优化 = 硬件系统 + 系统软件参数 + 数据库设计（**分区/分表/分库、物化视图、索引、SQL优化**）+ 应用软件（连接池、多副本等）；分布式优化还要考虑**通信代价**。

### 4. 分片：分区 / 分表 / 分库（案例特训 p36–40）

| | 分区 | 分表 |
|---|---|---|
| 共性 | ①都针对数据表；②都使用了分布式存储；③都提升了查询效率；④都降低了数据库的频繁I/O压力值 | （同左） |
| 差异 | **逻辑上还是一张表** | **逻辑上已是多张表** |

- **分库**：按业务拆分到不同数据库（用户库、商品库），分散访问压力。
- 三种分区方式：**范围分区 RANGE**（按用户编号段映射分区）、**散列分区 HASH**（对 key 做 hash/取余运算）、**列表分区 LIST**（按字段具体值，如长沙用户一个区、北京用户一个区）。
- **分区五优点**：①可存储更多数据；②数据管理方便（清理某年数据直接删该分区）；③精准定位分区查询、无需全表扫描，提高检索效率；④可跨多个分区磁盘查询提高吞吐量；⑤聚合函数查询时容易合并数据。

### 5. 分布式体系结构与透明性（案例特训 p41–42）

- 体系结构自上而下：**全局外模式 → 全局概念模式 → 分片模式 → 分布模式 → 局部概念模式 → 局部内模式**；上半部分（映像4以上）是分布式数据库**增加的**，下半部分是集中式数据库原有的。
- **分布透明性**四种：**分片透明性**（不关心如何分片存储）、**位置透明性**（无需知道数据存放的物理位置）、**复制透明**（不关心结点的复制情况）、**局部数据模型透明性/逻辑透明**（无需知道局部场地使用哪种数据模型）。
- 分片方式：**水平分片**（按记录/行分）、**垂直分片**（按字段/列分）、**混合分片**。

### 6. 两阶段提交协议 2PC（案例特训 p43–44）

- **两个阶段**：**表决阶段**（目的是形成一个共同的决定）；**执行阶段**（目的是实现协调者的决定）。
- **两条全局提交规则**：①只要有一个参与者撤销事务，协调者就必须做出**全局撤销**决定；②只有**所有**参与者都同意提交事务，协调者才能做出**全局提交**决定。
- 活动图要点：协调者写 begin_commit 日志 → 等待表决；参与者准备提交则写 ready 日志，否则写 abort；协调者根据表决结果写 commit/abort 日志并广播；参与者执行后回确认，协调者写 end_trans。

### 7. NoSQL 四类与关系数据库对比（案例特训 p46–48）

### 真题示范：线上药品销售系统（2021 · 反规范化 + Redis）

**题干摘要**（案例特训 p21–23，全文见 [[练习题-数据库设计案例]] Q3）：医药线上销售系统采用 MySQL+Redis 混合架构，规范化设计后表结构过细导致多表关联查询性能差。问题1 问反规范化设计方法及选型（9分）；问题2 问解决数据不一致的三种方法（9分）；问题3 问 Redis 数据类型选型与 Redis-MySQL 实时同步方案（7分）。

**参考答案（逐字）**：

> 【问题1】常见的反规范化技术包括：
> （1）增加冗余列：增加冗余列是指在多个表中具有相同的列，它常用来在查询时避免连接操作。
> （2）增加派生列：增加派生列指增加的列可以通过表中其他数据计算生成。它的作用是在查询时减少计算量，从而加快查询速度。
> （3）重新组表：重新组表指如果许多用户需要查看两个表连接出来的结果数据，则把这两个表重新组成一个表来减少连接而提高性能。
> （4）分割表：有时对表作分割可以提高性能。
> 用户查询商品信息应该采用：增加冗余列。
> 用户查询商品信息时，需要显示药品信息（药品表中），供应商信息（供应商表），库存信息（库存表中），此时查询的是药品表，但表中缺了供应商的信息和库存信息，可以通过增加冗余列的方式把这些信息并过来。以避免连接操作带来的查询性能下降。
>
> 【问题2】针对反规范化数据不一致问题，可采用的解决方案包括：
> 1、触发器数据同步。
> 2、应用程序数据同步。
> 3、批处理同步。
> 本系统应该采用 应用程序数据同步或者触发器数据同步方式。
>
> 【问题3】
> （1）热销药品排名适合用：ZSet，即有序集合类型。
> （2）①实时同步方案，先查缓存，查不到再从DB查询，并保存到缓存；更新缓存时先更新数据库，再将缓存设置过期。
> ②异步队列方式同步，可采用消息中间件处理。
> ③通过数据库插件完成数据同步。
> ④利用触发器进行缓存同步。

**解析**：这是三大题型的"集邮题"——问题1 考反规范化四技术（题型二），问题2 考数据不一致对策（题型二/三共用），问题3 考 Redis 数据类型与缓存一致性（题型三）。2021 年考情"规范化与反规范化技术、Redis"与本题完全对应。

> [!summary]- 三大题型题眼
> ① E-R 题：数据存储→实体、下划线→主键、冲突三分（属性/命名/结构）、1:1/1:n 归并、m:n 独立成表；
> ② 规范化题：候选码→主/非主属性→部分/传递依赖→2NF/3NF/BCNF；反规范化四技术+不一致三对策；
> ③ 缓存题：排名→ZSet、一致性四方法、读写分离（写/读/锁争用/数据冗余/一致性）、SBR/RBR/MBR、分区三分（范围/散列/列表）、2PC 表决+执行两规则、NoSQL 七对比四分类。
