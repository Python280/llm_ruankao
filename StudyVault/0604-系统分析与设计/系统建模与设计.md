# 系统建模与设计

> [!note] 考情（★★，讲义 p49-61）
> 讲义 p2 提要"**系统分析与设计★★**"；p51 细分：**界面设计★★、结构化设计★★、面向对象设计★★★**。选择题考点：内聚/耦合七类型排序与辨析（p55-56）、界面黄金三法则（p52，p53 有真题）、OO 设计七原则（p60，p61 有真题）、类的三种分类（p59）。案例题考点：DFD 补元素（实体/存储/数据流/加工）与用例图三关系。讲义 p49 另含论文题《论软件系统建模方法及其应用》。

## 一、软件系统建模概述（讲义 p49-50）

**软件系统建模（Software System Modeling）** 通过构建模型帮助开发人员**理解系统、抽取业务过程、管理系统复杂性**，并方便各类人员交流。它是**系统需求分析与系统实现之间架起的桥梁**——开发人员按模型开发出符合设计目标的系统，并基于该模型进行维护和改进。

三类建模方法（论文题"常用建模方法有哪几类"即此表）：

| 建模方法 | 中心思想 | 产出模型 | 特点与适用 |
|---|---|---|---|
| 结构化建模方法 | **以过程为中心** | **数据流图（DFD）** | 分析现有系统、定义新系统业务需求；**流程较为稳定**的系统 |
| 信息工程建模方法（数据库建模方法） | **以数据为中心**但过程敏感 | **实体联系图（ERD）** | 先研究分析**数据需求**，再研究过程需求；主要用于**数据建模** |
| 面向对象建模方法 | 数据＋过程集成为**对象** | **对象模型（UML）** | 消除数据与过程的人为分离；形成建模标准 **UML（统一建模语言）**，目前较常用 |

> [!tip] 一句话记忆
> 结构化看**流**（DFD）、信息工程看**数**（ERD）、面向对象看**对象**（UML）。

> [!tip] 来源：讲义 p49-50（官方 §5.3.1/§5.3.2 有对应方法论述）

## 二、结构化分析：数据流图 DFD（案例 p003-011）

### 1. 三模型一核心（案例 p003）

结构化需求分析（SA）的模型以**数据字典为核心**，外接三个模型：

| 模型 | 手段 | 元素 |
|---|---|---|
| **功能模型** | **数据流图（DFD）** | 数据流、加工、数据存储、外部实体 |
| **行为模型** | 状态转换图 | 状态（初态、终态）、事件 |
| **数据模型** | E-R 图 | 实体、联系 |

**数据字典（核心）**的条目：数据元素、数据结构、数据流、数据存储、加工逻辑、外部实体。官方定义：数据流图上**所有元素的定义和解释的文字集合**就是数据字典，其最重要作用是作为**分析阶段的工具**。

### 2. DFD 四元素（案例 p004）

| 元素 | 说明 | 图元 |
|---|---|---|
| **数据流** | 由一组固定成分的数据组成，表示数据的流向，用一个合适的名词反映其含义 | 水平箭头（→） |
| **加工** | 描述输入数据流到输出数据流之间的**变换**（输入做了什么处理变成输出） | 圆形、圆角矩形（两种记法） |
| **数据存储（文件）** | 表示暂时存储的数据；**流向文件＝写文件，流出＝读文件** | 双平行线、右开口矩形（两种记法） |
| **外部实体** | 存在于软件系统**外**的人员或组织 | 矩形 |

### 3. 分层：顶层图→0层图→子图（案例 p005-006、官方 §5.3.1）

- **顶层图**：只有 **1 个加工**（即整个系统），确定系统边界与内外关系，是进一步分解的基础；
- **0 层图**：把顶层加工分解为若干加工（编号 1、2、3…），可出现**数据存储**；
- **子图**：对 0 层图各加工继续分解（编号 1.1、1.2、2.1…），层层细化，直到每个加工只解决一个具体问题。

官方建模五步骤：①明确目标、确定系统范围 → ②建立顶层 DFD → ③构建第一层 DFD 分解图 → ④开发 DFD 层次结构图 → ⑤检查确认 DFD。

**官方检查规则**（判断 DFD 画得对错的）：

1. 父图中描述过的数据流**必须在相应子图中出现**；
2. 一个加工**至少有一个输入流和一个输出流**；
3. 一个存储**必定既有流入的数据流又有流出的数据流**；
4. 一个数据流**至少有一端是加工端**；
5. 分解原则：保持均匀的模型深度；按困难程度选择；**一个加工难以确切命名时，考虑重新分解**。

### 4. 平衡原则（案例 p007）

- **父图与子图之间的平衡**：子图的输入/输出数据流须与父图中对应加工的输入/输出一致；
- **子图内平衡**：每个加工有入有出。

三种异常现象（案例改错高频）：

| 异常 | 特征 |
|---|---|
| **黑洞** | 一个加工**只有输入**而无输出数据流 |
| **奇迹** | 一个加工**只有输出**而无输入数据流 |
| **灰洞** | 加工的输入数据流**无法通过加工产生输出流** |

### 5. DFD 答题技巧表 ★★★（案例 p009-011，案例题高频）

| 补什么 | 技巧 | 口诀 |
|---|---|---|
| **补实体** | 实体三类候选：①**人物角色**（客户、管理员、主管、经理、老师、学生）②**组织机构**（银行、供应商、募捐机构）③**外部系统**（银行系统、工资系统；开发中间件时的后台数据库） | 系统边界外找"人/组织/别的系统" |
| **补存储** | 存储的文字特征：「\*\*文件」「\*\*表」「\*\*库」「\*\*清单」「\*\*档案」 | 题干里找"**表、文件、库、清单、档案**"五词 |
| **补数据流** | ①**数据平衡原则**：顶层图与 0 层图互查，看是否有父有子无（或反之）的数据流；逐个检查加工是否只有入没有出、只有出没有入、输入无法产生对应输出 ②**按题目说明与图逐句匹配**：把说明中的实体与数据流标识出来后缩小对应范围，找出纰漏 | 先比父图，再对题干 |
| **补加工名** | 把该加工涉及的数据流在说明中标识出来，在**数据流名称所在的句子**里找「**动词+名词**」结构，分析能否作为加工（生成报告、发出通知、批改作业、记录分数；例外：物流跟踪、用户管理） | 句子中提取"动词+名词" |

> [!tip] 案例读题示范（案例 p009）
> 题干"数据管理员可通过中间件进行用户管理、操作管理和权限管理"→ 一句话锁定 **1 个外部实体＋3 个加工**；"用户信息（用户名、密码）存储在用户表中"→ 一句话锁定 **1 个存储**。说明中每一句话都能与图对应，逐句标识即可逼出纰漏。

> [!tip] 来源：案例特训 p003-011；官方教程 §5.3.1（印刷 p192-196）

## 三、用例建模（案例 p012-016）

### 1. UML 图分类（案例 p012）

- **静态图（结构图）**：类图、对象图、构件图、部署图、制品图、包图、组合结构图
- **动态图（行为图）**：用例图、顺序图、通信图、状态图、活动图、定时图、交互概览图

### 2. 用例图（案例 p013）

用例图描述一组**用例、参与者及它们之间的关系**：

- 从**用户角度**描述系统功能；
- **参与者**是外部触发因素（在系统边界外）；
- **用例**是功能单元（系统边界内的椭圆）。

### 3. 用例模型建立四步（案例 p014）

1. **识别参与者**——参与者：用户、组织、外部系统、**时间**（定时触发）；
2. **合并需求获得用例**；
3. **细化用例描述**；
4. **调整用例模型**（可选步骤）——用包含、扩展、泛化关系调整。

### 4. 用例描述（案例 p015）

用例描述表条目：**用例名称、用例 ID、角色、用例说明**（主要功能＋起始于…）、**前置条件、其它事件流、后置条件**。另配两张事件流表：

- **基本事件流**：按「参与者动作｜系统响应」两栏描述正常主流程；
- **异常事件流**：未输入、不存在、不正确等分支及其系统提示。

### 5. 用例三关系 ★★★（案例 p016）

| 关系 | 含义 | 术语 | 箭头方向 |
|---|---|---|---|
| **包含 \<\<include\>\>**（使用关系） | 从多个用例中**提取公共行为** | 提取出的公共用例＝**抽象用例**，原始用例＝**基本用例** | **基本用例 → 抽象用例**（虚线箭头） |
| **扩展 \<\<extend\>\>** | 一个用例明显混合**两种以上不同场景**，按分支拆分 | **基本用例**＋一个或多个**扩展用例** | **扩展用例 → 基本用例**（虚线箭头） |
| **泛化** | 多个用例共有类似的结构和行为，共性抽象为父用例 | 子用例**继承**父用例所有的结构、行为和关系 | 子用例 → 父用例（**空心三角实线**） |

> [!tip] 一句话记忆
> **包含指向被借的，扩展指向被扩的**：include 虚线箭头从基本用例指向被提取的抽象用例；extend 虚线箭头方向相反，从扩展用例指回基本用例——两者方向**正好相反**，常考。泛化是空心三角实线，子在下指向上方的父。

> [!tip] 来源：案例特训 p012-016

## 四、系统设计（讲义 p51-61）

### 1. 界面设计：人机界面黄金三法则（讲义 p52）★★

| 法则 | 要点 |
|---|---|
| **①置于用户控制之下** | 不强迫用户进入不必要/不希望的动作；交互灵活；**可中断和撤销**；技能级别增加时交互流水化并允许定制；隔离内部技术细节；允许用户与屏幕对象直接交互 |
| **②减少用户的记忆负担** | 减少对短期记忆的要求；建立有意义的缺省；定义直觉性的捷径；视觉布局基于**真实世界的隐喻**；以不断进展的方式揭示信息 |
| **③保持界面的一致性** | 允许用户将当前任务放入有意义的语境；应用系列内保持一致；**已建立的交互模型除非迫不得已不要改变** |

> [!warning] 真题眼（讲义 p53）
> "界面交互模型**应经常进行修改**"违反法则③——原文是"除非有迫不得已的理由，不要改变它"。

### 2. 结构化设计（讲义 p54-57）★★

**两阶段**：

- **概要设计【外部设计】**：把功能需求分配给软件模块，确定每个模块的**功能和调用关系**，形成**模块结构图**；
- **详细设计【内部设计】**：为每个具体任务选择适当的**技术手段和处理方法**。

**结构化设计原则**（四条）：

1. **模块独立性原则（高内聚、低耦合）**；
2. 保持模块的**大小适中**；
3. **多扇入，少扇出**；
4. **深度和宽度均不宜过高**。

> [!tip] 一句话记忆
> 扇入＝**调用它**的上级模块数（越多说明模块复用度越高）；扇出＝**它调用**的下级模块数（越少越好管）。"**多扇入、少扇出**"。

**内聚七类型（从高到低）**（讲义 p55）：

| 内聚类型 | 描述 |
|---|---|
| 功能内聚 | 完成一个**单一功能**，各部分协同工作、缺一不可 |
| 顺序内聚 | 处理元素相关，而且必须**顺序执行** |
| 通信内聚 | 所有处理元素集中在**同一个数据结构**的区域上 |
| 过程内聚 | 处理元素相关，而且必须按**特定的次序**执行 |
| 时间内聚（瞬时内聚） | 任务必须在**同一时间间隔**内执行 |
| 逻辑内聚 | 完成**逻辑上相关**的一组任务 |
| 偶然内聚（巧合内聚） | 完成一组**没有关系或松散关系**的任务 |

**耦合七类型（从低到高）**（讲义 p56）：

| 耦合类型 | 描述 |
|---|---|
| 非直接耦合 | 两模块间无直接关系，联系完全通过**主模块的控制和调用**实现 |
| 数据耦合 | 一组模块借助参数表传递**简单数据** |
| 标记耦合 | 一组模块借助参数表传递**记录信息（数据结构）** |
| 控制耦合 | 传递的信息中包含**用于控制模块内部逻辑**的信息 |
| 外部耦合 | 一组模块都访问**同一全局简单变量**，且不通过参数表传递 |
| 公共耦合 | 多个模块都访问**同一个公共数据环境** |
| 内容耦合 | 直接访问另一模块**内部数据**；不经正常入口进入其内部；两模块**代码重叠**；一个模块有多个入口 |

> [!warning] 冲突两说：耦合七类型的第 5 种
> 讲义（考试标准）七类型含**外部耦合**（同一全局简单变量）；官方教程第二版表 5-1 无外部耦合，代之以**通信耦合**（一组模块共用一组输入信息，或输出需整合形成完整数据）。**考试跟讲义**：非直接/数据/标记/控制/外部/公共/内容。

> [!important] 高频辨析
> - **顺序内聚 vs 过程内聚**：顺序＝前一步输出即后一步输入、必须顺序执行；过程＝按特定次序执行但元素间不一定有数据传递。
> - **数据耦合 vs 标记耦合**：传**简单数据**是数据耦合，传**记录/数据结构**是标记耦合。
> - **外部耦合 vs 公共耦合**：同一**全局简单变量**＝外部；同一**公共数据环境**（全局数据结构、共享通信区等）＝公共。

**模块四要素**（讲义 p57）：**输入和输出**（来源与去向都是同一个调用者）、**处理功能**（把输入转换成输出所做的工作）、**内部数据**（仅供该模块本身引用）、**程序代码**（实现模块功能的程序）。

**官方补充**（官方 §5.3.1）：

- **系统结构图（SC）** 又称模块结构图，是**概要设计阶段的工具**，反映系统功能实现与模块间的联系、通信及层次结构，可由 DFD 按规则导出；
- 详细设计表示工具：**图形工具**（业务流图、程序流程图、**N-S 盒图**、**PAD 图**）、**表格工具**（判定表）、**语言工具**（伪码/**PDL 结构化语言**）；
- 模块一般具有**功能、逻辑和状态**三个基本属性：功能＝"做什么"，逻辑＝内部"怎么做"，状态＝使用时的环境和条件。

### 3. 面向对象设计（讲义 p58-60）★★★

**基本过程**（p58）：分析模型（用例模型、领域模型）→ 设计师四活动（**设计用例实现方案、设计技术支撑实施、设计用户界面、细化设计模型**）→ 设计模型（**架构图用包图表示、用例实现图用交互图表示**、完整精确的类图，以及状态图、活动图等）。

**类的分类**（p59）：

| 类的分类 | 构成 | 例 |
|---|---|---|
| **边界类** | 机器接口→API 接口；人机交互→用户界面 | 显示屏、窗体、打印机接口、通信协议、对话框、菜单、购物车、报表、二维码 |
| **控制类** | 应用逻辑、业务逻辑、数据访问逻辑 | 身份验证器 |
| **实体类** | 数据 | 学员类、课程类 |

> [!important] 三类辨析（官方 §5.3.2）
> - **实体类**：映射需求中的实体，保存**需永久存储**的信息；用业务领域术语命名（一般是名词），可从 SRS 中与**数据库表**对应的名词着手寻找；用例模型向领域模型转化中，官方原文称"一个参与者一般对应于实体类"。
> - **控制类**：控制用例工作，一般由**动宾结构短语**转化而来（用例"身份验证"→控制类"**身份验证器**"）；控制对象行为具有**协调性**，用例执行时产生、执行完毕后常消亡；通常没有属性但一定有方法。
> - **边界类**：封装用例内、外流动的信息，位于**系统与外界的交接处**；每个参与者和用例的交互**至少有一个边界类**；把系统与外部环境变更分隔开，使变更不影响系统其他部分。

**面向对象设计七原则**（p60）：

| 原则 | 一句话 |
|---|---|
| **单一职责原则** | 设计目的单一的类 |
| **开放-封闭原则** | **对扩展开放，对修改封闭** |
| **李氏（Liskov）替换原则** | 子类可以替换父类 |
| **依赖倒置原则** | 依赖于**抽象**而非具体实现；**针对接口编程**，不针对实现编程 |
| **接口隔离原则** | 使用多个专门的接口比使用单一的总接口要好 |
| **组合重用原则** | 尽量使用**组合**而不是继承达到重用目的 |
| **迪米特（Demeter）原则**（最少知识原则） | 一个对象应当对其他对象有尽可能**少的了解** |

> [!warning] 真题眼（讲义 p61）
> "每个类都应当尽可能**提高**对其属性和方法的访问权限"**违反**最少知识原则——最少知识要的是尽量少暴露、降低引用，而不是放大访问权限。
