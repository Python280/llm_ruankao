### 8.8 分布式缓存技术 Redis

【基础知识点】

1. 基本概念：Redis 是一种分布式缓存技术，在本书8.5节中也是一种键值对数据库类型；基于内存读写，性能比基于磁盘读写的数据库高很多，适合缓存高频热点数据提高读性能，降低对数据库服务器的查询请求；以 key-value（键值对）形式保存数据，键（key）是字符串，值（value）可以是任意类型数据（整型、字符型、数组、列表、集合等）；例键值对（"20231234","张珂"），key 是唯一标识，value 是实际存储内容。
2. 数据类型：主要包括 string、hash、set、list、zset、pub/sub 类型。
   - （1）string 类型：Redis 基本类型，可用于缓存层或计数器（视频播放量、文章浏览量等）。
   - （2）hash 类型：代替 string 类型，节省空间，描述用户信息较为方便。
   - （3）set 类型：无序集合，每个值不能重复，可用于去重、抽奖、初始化用户池等。
   - （4）list 类型：双向链表结构，可模拟栈、队列等形式，可用于回复评论、点赞。

3. 访问方式：引入 Redis 后热点数据存放在 Redis 中，但存在"一份数据存放了多个位置"，要考虑一致性问题。读写数据的基本步骤：
   - （1）读数据：①根据 key 读缓存；②读取成功则直接返回；③若 key 不在缓存中，则根据 key 读数据库；④读取成功后，写缓存；⑤成功返回。
   - （2）写数据：①根据 key 值写数据库；②成功后更新缓存 key 值；③成功返回。
4. 过期策略：一般设置 Redis 缓存空间大小，不让数据无限制存放；设置过期时间的数据采用两种方式淘汰：
   - （1）定期删除：Redis 每隔一段时间随机抽取一些设置了过期时间的 key（无法遍历所有 key，否则负担大）；会导致一些 key 到了过期时间仍没有被删除。
   - （2）惰性删除：查询 key 时 Redis 对 key 检测，达到过期时间则删除；缺点是过期的 key 若没有被访问就一直无法被删除，一直占用内存。
   - 其他淘汰机制：
     - volatile-lru（最近最少使用）：从已设置过期时间的 key 中，移出最近最少使用的 key 进行淘汰。
     - volatile-lfu（最不经常使用）：从 key 中选择最不经常使用的进行淘汰。
     - volatile-random（随机淘汰算法）：从已设置过期时间的 key 中随机选择 key 淘汰。
     - volatile-ttl（生存时间淘汰）：从已设置过期时间的 key 中，移出将要过期的 key。
     - allkeys-lru：从所有 key 中选择最近最少使用的进行淘汰。
     - allkeys-lfu：从所有 key 中选择最不经常使用的进行淘汰。
     - allkeys-random：从所有 key 中随机选择 key 进行淘汰。
5. 数据持久化：服务器宕机则内存数据全部丢失；从后端数据库恢复有两个问题：频繁访问数据库带来巨大压力；从慢速数据库读取性能比不上 Redis，应用响应变慢。故实现持久化至关重要。持久化方式有两种，见表8.8。
6. 缓存异常问题：Redis 在提高数据查询效率与保护数据库方面至关重要，但实际应用中可能出现异常；本节总结常见异常问题与解决方案。

缓存异常问题：

- （1）缓存穿透：大量请求访问了没有缓存的 key（key 在 Redis 里不存在），请求直接访问数据库，压力增大。可能原因：
  - 1）恶意攻击，造成大量访问不存在的 key。例如登录时使用无效用户名，在软考网站查询成绩时输入不存在的身份证号、准考证号。
    - 解决方案：①针对比较少的请求来源 IP，主动限制其访问次数，或拉入黑名单；②应用程序检查 key 的合法性，提前拒绝不合法的请求；③使用布隆过滤器。
  - 2）大量请求访问数据库里有但 Redis 没有的 key。例如新业务刚上线，Redis 是空的。
    - 解决方案：①预热 Redis，运行批处理脚本将可能会大量访问的数据预先加载到 Redis，业务再"开张"；②在最前端进行流量控制，逐步把请求释放进来，给出一段时间让 Redis 逐步加载热数据；③如果是在数据库里也没有的 key，也需要在 Redis 中设置 key，使其值为 null 或空。
- （2）缓存雪崩：大量请求访问到缓存中的 key，key 存在但同时到了过期时间，请求直接访问数据库，压力增大；可能进而影响一系列雪崩，影响到上下游所有应用服务。可能原因：
  - 1）Redis 故障。比如 Redis 宕机，网络出现抖动等。
    - 解决方案：①使用主从复制提高可用性，使用 cluster 集群方案降低故障时影响的范围；②如果出现故障，则可以采取服务降级、熔断、限流等措施。
  - 2）大量的 key 采用了相同的过期时间。例如在同一时刻设置了大量的 key，但过期时间都是5分钟。
    - 解决方案：过期时间加上一个随机值，使得众多 key 均匀过期。
- （3）缓存击穿：少量热点的 key 缓存时间失效了，使得请求直接访问数据库。
  - 可能原因：热点的 key 设置了太短的过期时间。例如秒杀业务下的"库存数量"。
  - 解决方案：①将 key 设置较长的过期时间，非常重要的 key 设置永久有效，但需解决好与数据库中 key 的一致性问题；②使用分布式锁，热点 key 失效时控制访问后端数据库的流量，只允许一个请求访问数据库取出最新的 key 存放到 Redis，其他请求则必须（接下页）
